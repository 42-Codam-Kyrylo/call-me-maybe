# Обьяснения 

## 1. Что такое Vocabulary (Словарь) и как его готовить в Production?

**Что это такое:**
Для языковой модели не существует букв, слов или строк. Текст для нее — это просто массив целых чисел. Vocabulary (словарь) — это "переводчик" или таблица соответствий между числом (ID) и куском текста (токеном). Например, ID 124 может означать токен " sum", а ID 90 — символ `{"`. В рамках проекта ты получаешь путь к этому словарю через метод `get_path_to_vocab_file()`.  

**Где и как его хранить:**
- **Только не в Numpy:** Библиотека numpy создана для тяжелой математики над матрицами чисел (например, для обработки логитов). Хранить строки разной длины в массивах Numpy крайне неэффективно.  
- **Идеальное решение:** Обычный Python dict (словарь) или даже простой list (если ID токенов идут строго по порядку от 0 и без пропусков). Поиск по ключу в dict работает за время $O(1)$ — это максимально быстро.
- **Жизненный цикл:** Да, ты считываешь JSON-файл словаря ровно один раз при запуске программы и сохраняешь его в переменную. Читать файл с диска на каждый сгенерированный токен — это убийство производительности.

**Как это делают в реальном BigTech:**
Это абсолютно продакшен-подход. Дело в том, что размер словаря не растет пропорционально размеру "мозгов" модели. Даже у гигантских моделей вроде GPT-4 или Llama 3 словарь состоит всего из 50 000 – 128 000 токенов. В оперативной памяти текстовый словарь на 100 тысяч коротких слов занимает смешные несколько мегабайт. Поэтому в реальном мире (например, в популярной библиотеке tokenizers от HuggingFace) словарь точно так же загружается в память один раз при старте сервиса. Разница лишь в том, что в проде этот хэш-мап написан на Rust или C++ для дополнительной скорости, но концептуально ты сейчас делаешь ровно то же самое.

## 2. Что такое Конечный автомат (FSM - Finite State Machine)

Это базовая концепция из Computer Science для создания надежной логики и парсеров.

**Идея:**
Представь систему, которая в любой момент времени может находиться только в одном из заранее заданных состояний (States). Чтобы перейти в другое состояние (Transition), система должна получить строго определенный сигнал. Если приходит "неправильный" сигнал — система его блокирует.

**Пример из жизни: Турникет в метро.**
У него есть всего два состояния: ЗАКРЫТ и ОТКРЫТ.
- Если он ЗАКРЫТ и ты пытаешься пройти (сигнал "Толкать") — он не пустит (состояние не меняется).
- Если он ЗАКРЫТ и ты прикладываешь карту (сигнал "Оплата") — он переходит в состояние ОТКРЫТ.
- Если он ОТКРЫТ и ты прошел (сигнал "Проход") — он возвращается в состояние ЗАКРЫТ.

**Как это работает для JSON в твоем проекте:**
Тебе нужно написать класс, который будет отслеживать, какую часть ответа мы сейчас собираем. Твой автомат будет контролировать, какие токены можно разрешить языковой модели.

**Пример состояний для твоего автомата:**
- **Состояние `WAITING_START`:** Мы только начали. Разрешено: Только символ `{`. Никакие другие буквы или цифры недопустимы. Переход: Если получаем `{`, переходим в `WAITING_NAME_KEY`.
- **Состояние `WAITING_NAME_KEY`:** Ждем ключ имени функции. Разрешено: Строка `"name": `. Переход: Как только получили, переходим в `WAITING_FUNCTION_VALUE`.
- **Состояние `WAITING_FUNCTION_VALUE`:** Ждем название. Разрешено: Только те слова, которые есть в списке доступных функций (например, `fn_add_numbers`). Переход: Как только функция выбрана, ждем запятую.

Именно FSM гарантирует, что модель не сможет сгенерировать невалидный JSON, потому что на каждом шаге автомат жестко ограничивает выбор токенов в зависимости от текущего состояния.  

Если с загрузкой словаря (первым шагом) всё понятно, попробуем набросать логические состояния твоего будущего FSM на бумаге?

## numpy usage

Метод `get_logits_from_input_ids()` возвращает обычный питоновский список (`List[float]`) огромного размера — по одному числу (вероятности) для каждого возможного токена в словаре модели. Если бы ты обходил этот массив обычным циклом `for` в Python на каждом шаге генерации, программа работала бы мучительно долго. numpy позволяет делать это мгновенно с помощью векторизованных операций.  

**Вот две главные математические задачи, которые numpy закроет для тебя в этом проекте:**
- **Маскирование логитов (Constrained Decoding):** Твой конечный автомат (FSM) вместе со словарем определяет список "разрешенных" ID токенов. С помощью numpy ты можешь в одну-две строчки кода найти все индексы, не входящие в этот список, и приравнять их значения к минус бесконечности (`-inf`).  
- **Поиск победителя (Argmax):** После того как все токены, ломающие синтаксис JSON, получили оценку минус бесконечность, тебе нужно узнать, какой из оставшихся токенов модель считает самым вероятным. Функция `np.argmax()` моментально найдет индекс элемента с максимальным значением в массиве.  

**Как выглядит схема взаимодействия:**
1. LLM выдает сырые логиты.  
2. Ты оборачиваешь этот список в массив numpy.
3. Твой FSM говорит: "Сейчас ждем число".
4. Ты достаешь из словаря ID всех токенов, которые являются числами.
5. numpy физически блокирует всё остальное, проставляя `-inf`.  
6. `numpy.argmax()` выдает ID токена-победителя, который ты добавляешь в свой JSON.

Получается идеальный симбиоз: FSM выступает в роли мозга, который понимает контекст и знает грамматику, а numpy работает как грубая сила, моментально отсекающая математический "мусор".

## Constrained decoding

определять, что валидно, а что нет, нужно **только динамически**, опираясь на текстовое значение токенов из словаря. И здесь тебе как раз пригодится модуль `re` (регулярные выражения), о котором говорил автор сабжекта в Slack.

Вот как выглядит этот процесс на практике:

### 1. Как динамически находить токены

Представь, что твой словарь — это огромный питоновский словарь (хэш-таблица), где ключ — это текст токена, а значение — его ID.

Когда твой конечный автомат (FSM) переходит в состояние «Жду число» (потому что в схеме `functions_definition.json` указан `"type": "number"`), ты делаешь следующее:

* Проходишься циклом по всем 150 000+ ключам (строкам) твоего словаря.
* Для каждой строки проверяешь: состоит ли она **только** из допустимых для числа символов? (Цифры от `0` до `9`, точка, возможно минус). Можно использовать регулярку вроде `re.fullmatch(r"[-0-9.]+", token_text)`.
* Если текст токена прошел проверку — ты добавляешь его ID в список `allowed_ids`.
* Все остальные ID маскируешь в минус бесконечность (`-inf`) с помощью `numpy`.



### 2. Оптимизация (Кэширование)

Бегать регулярками по 150 000 строкам словаря на *каждый* сгенерированный токен — это очень медленно.
Поскольку словарь статичен (загружается один раз), ты можешь **закэшировать** эти группы при старте программы.

На этапе инициализации ты можешь один раз пройтись по словарю и создать удобные множества (`set`):

* `NUMBER_TOKEN_IDS` = множество всех ID, которые содержат только цифры/точки.
* `WHITESPACE_TOKEN_IDS` = множество всех ID, которые являются пробелами, табами или переносами строк.

Тогда в процессе генерации, когда FSM говорит "здесь нужно число", ты не вычисляешь ничего заново, а просто берешь готовое множество `NUMBER_TOKEN_IDS` и разрешаешь только их.

### 3. Работа с префиксами (Самое сложное)

Для чисел всё просто — они состоят из цифр. Но что делать, когда ты ждешь конкретную строку, например `{"name": "`?
Как писал автор задания, токенизатор может собрать эту строку разными путями. Твоя задача — разрешить **любой токен, текст которого является началом (префиксом) нужной тебе строки** (или наоборот, нужная строка является началом токена).

Например, мы ждем `{"name": "`:

* Токен `{"` — валиден (это начало нашей строки). Разрешаем его ID.
* Токен `{` — тоже валиден.
* Токен `{"name": "fn_` — **НЕ** валиден, потому что он слишком длинный и содержит лишний кусок `fn_`, который мы пока не просили.

**Итог:** Ты не гадаешь по ID. Твой алгоритм работает исключительно с **текстовыми значениями** токенов из словаря, отбирает те, которые синтаксически подходят под текущее состояние автомата, собирает их ID в кучу и передает в `numpy` для маскирования логитов.

Звучит логично? Как думаешь, написать регулярку для поиска всех подходящих токенов-чисел будет легко, или стоит разобрать пример того, как это сделать в коде?

Разница между именами функций и строковыми параметрами огромна, и к ним нужны два совершенно разных подхода.

Давай разберем оба случая, потому что именно здесь многие студенты ломают голову.

### 1. Имена функций: Строгий выбор (Закрытый список)

Имя функции — это **не** просто любая строка. Модель не имеет права выдумывать имена. Она обязана выбрать строго одно из имен, прописанных в твоем файле `functions_definition.json`.

Здесь регулярка на "любые буквы" не сработает, иначе модель сгенерирует какую-нибудь `fn_hello_world`, которой нет в схеме, и всё сломается.

**Как фильтровать:**
Используем **поиск по префиксу** (как раз то, о чем говорил автор сабжекта в Slack).
Представь, что у тебя в схеме есть только две функции: `fn_add_numbers` и `fn_greet`.

1. Модель сгенерировала (или ты вклеил) начало: `fn_`
2. Твой алгоритм берет каждый токен из словаря и мысленно приклеивает его к `fn_`.
3. Допустим, мы проверяем токен `"ad"`. Получается строка `"fn_ad"`.
4. Алгоритм спрашивает: *"Является ли `"fn_ad"` началом (префиксом) для `fn_add_numbers` или `fn_greet`?"*. Да, является! Значит, токен `"ad"` **разрешен**.
5. Проверяем токен `"xyz"`. Получается `"fn_xyz"`. Это не подходит ни под одну функцию. Значит, этот токен **блокируем** (`-inf`).



Таким образом, ты программно зажимаешь модель в тиски: она физически сможет выбрать токены только из тех букв, которые ведут к легальному имени функции.

### 2. Строковые параметры: Свободный полет (Открытый список)

А вот здесь всё иначе. Если в `functions_definition.json` для аргумента указан `"type": "string"`, это значит, что внутри параметра модель может написать **любой** текст (например, `"hello world"`, `"Shrek"`, `"John 123"`).

Здесь мы действительно используем логику "разрешить почти всё, что является строкой", но с одной критической оговоркой: **соблюдение синтаксиса JSON**.

**Как фильтровать:**
Твой FSM знает, что сейчас генерируется значение строки (мы находимся между двумя кавычками `"..."`).
В этот момент ты разрешаешь **практически весь словарь**, КРОМЕ токенов, которые ломают JSON:

1. **Запрет на неэкранированные символы:** Ты блокируешь токены, которые содержат реальный перенос строки (Enter), потому что в JSON переносы строк внутри значений должны писаться как `\n`.
2. **Контроль кавычек:** Это самое важное. Токен с кавычкой `"` — это триггер. Если модель генерирует токен, содержащий `"`, твой автомат должен понять: *"Ага, строка закончилась!"*. И сразу после этого FSM должен запретить любые текстовые токены и требовать либо запятую `,`, либо закрывающую скобку `}`.



**Итог:**

* **Имена функций:** Проверяешь токены на то, являются ли они кусками заранее известных легальных названий из схемы.


* **Строковые параметры:** Разрешаешь почти любые текстовые токены, но следишь за кавычками `"` и запрещенными в JSON спецсимволами, чтобы не сломать парсер на выходе.



Учитывая твой бэкграунд работы со строками на C в Codam, логика с префиксами для имен функций (`strncmp` vibe) должна показаться тебе очень знакомой. Как тебе концепция, всё встает на свои места?

## Global flow

Вот как выглядит полный жизненный цикл твоей программы, от запуска скрипта до получения финального файла, если собрать все концепции воедино.

### 1. Инициализация и Подготовка

На этом этапе программа собирает весь необходимый контекст для работы алгоритмов.

* **Загрузка словаря:** Программа вызывает `get_path_to_vocab_file()`, считывает JSON словаря и сохраняет его в оперативную память (например, в `dict`).


* **Парсинг схем:** Читается файл `functions_definition.json`. Pydantic-модели валидируют описания функций, их имена и строгие типы аргументов.


* **Чтение промптов:** Скрипт загружает массив текстовых запросов пользователей из `function_calling_tests.json`.



---

### 2. Главный цикл обработки

Для каждого отдельного промпта (например, "Greet shrek") запускается изолированный процесс:

* **Смысловой промпт:** Формируется базовый текст для модели (оригинальный запрос пользователя + текстовое описание доступных функций).


* **Кодирование (encode):** Этот текст прогоняется через метод `encode()`, превращаясь в массив ID токенов, который станет стартовой точкой (контекстом) для генерации.



---

### 3. Движок Constrained Decoding (Работа FSM)

Здесь начинается генерация структуры, управляемая конечным автоматом (FSM):

* **Слияние (Coalescence):** FSM знает, что синтаксис жесткий. В массив контекста напрямую вклеиваются ID токенов для строки `{"name": "` без вызова нейросети.
* **Генерация имени:** Теперь запрашиваются логиты (`get_logits_from_input_ids()`). FSM фильтрует словарь и оставляет `>-inf` только у тех токенов, которые являются началом валидного имени функции из схемы. Токен-победитель добавляется в контекст.


* **Переход к параметрам:** Снова работает ручное слияние. В историю напрямую вклеиваются ID токенов для строки `", "parameters": {`.
* **Генерация аргументов:** FSM смотрит на типы аргументов выбранной функции. Для каждого параметра запрашиваются логиты, FSM маскирует "мусор" (например, блокирует строковые токены, если ожидается `"type": "number"`), и нейросеть пошагово выдает значения.


* **Закрытие объекта:** Программа вклеивает финальный токен `}`.

---

### 4. Финализация и Вывод

На этом этапе сгенерированные токены превращаются в требуемый результат.

* **Парсинг результата:** Полученный массив ID декодируется в текст и конвертируется в Python-объект через `json.loads()`.
* **Сборка:** К полученному объекту добавляется оригинальный ключ `prompt`.


* **Запись на диск:** После завершения обработки всех запросов, итоговый список сохраняется в файл `data/output/function_calling_results.json` строго по требуемому формату.



Какой из этих четырех этапов кажется тебе наиболее объемным для реализации в коде прямо сейчас?

## How to call ai

Отличный вопрос. Здесь мы подходим к главной иллюзии искусственного интеллекта. Секрет в том, что маленькая модель (на 0.6B параметров) на самом деле **ничего не понимает** в человеческом смысле. Она не осознает, что является агентом, который должен парсить схемы и вызывать функции. Она умеет делать только одно: продолжать текст.

Давай разберем, как мы формируем этот текст, чтобы заставить ее сделать правильный выбор.

### 1. Что такое «оригинальный запрос пользователя»?

Это просто текст, который лежит под ключом `"prompt"` в твоем входном файле `function_calling_tests.json`.
Например: *"What is the sum of 2 and 3?"* или *"Reverse the string 'hello'"*.

Если ты передашь модели только эту строчку, она попытается просто ответить на вопрос текстом, потому что не знает о существовании функций.

### 2. Как модель понимает, что нужно делать? (Магия промптинга)

Чтобы модель выбрала нужную функцию из твоего `functions_definition.json`, ты должен перед началом генерации программно склеить из этих двух файлов **единый текстовый контекст**.

Этот контекст (System Prompt) обычно выглядит примерно так:

```text
You have access to the following functions:
1. fn_add_numbers(a: number, b: number): Add two numbers together and return their sum.
2. fn_greet(name: string): Generate a greeting message for a person by name.
3. fn_reverse_string(s: string): Reverse a string and return the reversed result.

User request: What is the sum of 2 and 3?

Function call:

```

Ты собираешь этот текст в Python (парсишь `functions_definition.json` и красиво форматируешь его в строку), приклеиваешь снизу запрос пользователя и пропускаешь всё это через токенизатор (`encode`).

### 3. Как она понимает, что нужно собирать JSON?

А вот тут вступает в игру наша оптимизация — **Coalescence (слияние)**, которую мы обсуждали ранее.

Ты не ждешь, пока модель сама решит написать JSON. Помнишь правило из сабжекта? *"Ваше решение НЕ ДОЛЖНО полагаться на то, что модель спонтанно выдаст правильный JSON из промпта"*.

Ты берешь этот большой контекст и программно приклеиваешь к нему в самый конец начало твоего JSON: `{"name": "fn_`.

В итоге модель видит вот такой текст (в виде токенов):

> *... (список функций) ...*
> *User request: What is the sum of 2 and 3?*
> *Function call:*
> `{"name": "fn_`

**Что происходит в "голове" нейросети в этот момент:**
Она видит, что текст оборвался на префиксе `fn_`. Она "читала" чуть выше, что в списке доступных инструментов есть `fn_add_numbers`. Поскольку контекст вокруг математики ("sum of 2 and 3"), вероятности (логиты) в её нейронной сети для токена `add` взлетят до небес.

### 4. Роль Constrained Decoding

Модель может попытаться сгаллюцинировать и захотеть выдать `fn_calculate`, потому что слово `sum` ассоциируется у нее с калькулятором.
Но тут вступает твой конечный автомат (FSM)! Он смотрит на логиты и говорит: *"Нет, дружище, у нас в списке есть только `add_numbers`, `greet` и `reverse_string`. Я запрещаю тебе печатать `calculate` (ставлю вероятность -inf)"*. И модели не остается ничего, кроме как выбрать токен `add`, у которого тоже была высокая вероятность благодаря нашему текстовому промпту.

**Итог:** Модель не принимает самостоятельного осознанного решения "собрать финальный аутпут".

1. Твой промпт подсказывает ей контекст (какие есть функции и что хочет юзер).
2. Твои вклеенные скобки `{"name": "` загоняют ее в синтаксис JSON.
3. Твой алгоритм Constrained Decoding (FSM) физически блокирует любые имена и токены, которых нет в схеме.
